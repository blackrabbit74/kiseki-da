## LP-1 意図と完了条件を先に書く（Intent before execution）

**原則**: 非自明なタスク（複数ステップ、ファイルや外部への副作用、再開の可能性があるもの）は、着手前に「目標・完了条件（各条件に検査方法と反証条件）・制約・対象外・仮定・未確定点」を ≤800 tokens のタスクカードに書く。自明なタスクには書かない。不足情報は「答えによって成果物が変わるか」で判定し、最大 3 問まで一度に一つずつ聞く。聞かないときは仮定を一行で明示する。

**必要な理由**: 未指定タスクで対話すると成功率が最大 +74%（T-J8）、要件を逐次に与えると −39%（T-A5）。モデルは既定ではほぼ質問しない（T-J4, T-J10）。書かれた仕様から再開するのは Claude Code の公式推奨（T-J11）。LifeOS の「最大 3 問、`proceed` 上書き、曖昧性フラグ」（L-03）は良い実装であり継承する。

**防ごうとする失敗**: 確信を持って間違った方向へ進む出力、早期に固定した仮定からの非回復（T-A5）、会話に依存した再開の失敗、検証不能な「完了」。

**採用する機構**: タスクカード（AD-5）。質問の期待効用ルール（H-H1, T-J5）: 答えで成果物が変わるなら聞く、変わらないなら仮定して明示。仮定はイベントに記録し、後の訂正と突き合わせる。

**採用しない機構**: 17 セクションの ISA、完備ゲート、効力ティア分類器、三仮説の必須化、全タスクへの科学ループ、教義ファイルの読込。

**測定方法**: タスクあたりの訂正回数と差し戻し数、質問の有用率（答えが成果物を変えた割合）、仮定フラグの正答率、再開タスクの成功率。目標: 有用率 ≥50%、R≥1 タスクの訂正 ≤1 回。

## LP-2 証拠なき完了はない（Evidence-gated done）

**原則**: 副作用のあるタスク（R≥1）で「完了」を主張するときは、各完了条件に対してツール由来の証拠（テスト結果、差分の読み返し、HTTP 応答、実ブラウザの確認、read-back）をイベント ID で結びつける。証拠がなければ「未検証」と言う。「should work」は禁止。自己採点と、同一モデルによる自己審査は完了の根拠にならない。反復は有界（既定 3 回）で、外部信号がないときは反復しない。

**必要な理由**: 内発的自己修正は精度を下げ（T-D3: 95.5→89.0）、prompted LLM のフィードバックによる自己修正の成功例はない（T-D5）。ツール検証付き批評は有効（T-D4）。LLM 判定器は寛大で自己選好する（T-D9, T-D10）。LifeOS の自己採点は 99.4% 一定の演技だった（L-33）。

**防ごうとする失敗**: 検証の演技、根拠なき断定、テストを走らせずに「done」、自己審査の通過、無限反復。

**採用する機構**: 証拠モダリティ表（L-07 を継承）、タスクカードの `evidence` 列とイベント ID の突合、構造化ストップゲート（AD-6）、有界反復。

**採用しない機構**: 散文の完了主張を正規表現で検出するゲート（誤検知で死んだ SuccessClaimGate, L-13）、自己採点、反省の必須行、ナッジ hook。

**測定方法**: R≥1 タスクの証拠充足率、ストップゲートのブロック数と誤ブロック率（目標 <20%）、完了主張後の利用者による差し戻し率、pass^k（同一 evals の反復成功率、T-E11）。

## LP-3 常駐は最小、取得は必要時（Minimal resident context, just-in-time retrieval）

**原則**: セッション開始時に常駐する文脈は ≤2.5K tokens（対話方針 ≤800、キャラクター ≤220、進行中カード要約 ≤400、時刻と取得コマンド ≤150、残りは制約・選好）。プロンプトごとの自動注入は行わない。それ以外は `kiseki-da search` や `kiseki-da task show` で要求時に、出典と日付付きで取得する。何を読み込んだかは毎セッション「文脈マニフェスト」として記録する。

**必要な理由**: 関連 300 tokens の方が全履歴 113K より高精度（T-A2）、長さだけで 13.9–85% 低下（T-A6）、エージェント課題は 8K→128K で 96%→34%（T-A7）、指示数の増加で遵守率は単調低下（T-G6/G7）、取得文脈があると質問が減る（T-J10）。LifeOS は自ら ≈20K tokens の静的ロードを問題視し（L-37, L-38）、毎プロンプト注入を「数十回重複」として修正した（L-35）。

**防ごうとする失敗**: context rot、Lost in the Middle、質問の抑制、トークン浪費、compaction での文脈喪失、不要なファイル参照。

**採用する機構**: `ctx build` の予算制御（AD-2）、要求時の BM25 検索（AD-4）、文脈マニフェストのイベント記録、compaction 後の再注入（Claude Code は SessionStart hook が全 source で発火、O-CC2）。

**採用しない機構**: セッション開始時の一括注入、TELOS 全文の @import、ホット層の毎プロンプト注入、スキル一覧の無制限化、教義ファイルの自動読込。

**測定方法**: セッションあたり入力トークン、常駐トークン数（テストで ≤2.5K を強制）、不要参照率（読み込んだが引用されなかった文脈の割合）、実験 E1/E2 でのタスク成功率と質問率。

## LP-4 記憶は出典・日付・確度・期限付きの少数の事実（Provenanced, bounded memory）

**原則**: 永続記憶は `profile.toml` の ≤60 件に限り、各項目は `source`（user-stated / approved-inference / document）、`recorded_at`、`confidence`、`review_by` を持つ。書込は利用者の明示発言（「今後は」「覚えて」「訂正」）から生成した候補、または利用者が承認した候補のみ。推論した記憶は自動保存しない。同一キーの更新は上書きだが、旧値と訂正イベントは履歴に残す。出典で決着しない衝突は解決せず、両方を提示する。失効した項目は常駐から外れ、検索では `[stale]` と表示する。その他の履歴はすべて `events.jsonl` にあり、検索で取得する。

**必要な理由**: 記憶の失効判定は最良で 55.2%（T-C13）、抽出記憶は追従を最大 25 倍にし（T-C14）、通常クエリだけで記憶を汚染できる（T-C11）。商用記憶層は BM25 に負ける（T-C9）。選好は構築されドリフトする（H-E8, H-H8）。保存しても見えない項目は使われない（H-G6）。LifeOS は自動適用で 48 時間に 12 ルールを失い（L-38）、出典タグと「出典なき衝突は解決しない」規則を持っている（L-09）— 後者を継承し前者を廃する。

**防ごうとする失敗**: 誤った記憶の固定化、古い情報の混入、追従の増幅、記憶経由の注入、要約の繰り返しによる情報損失（T-H3 の類推）、整理労力の浪費（H-G5）。

**採用する機構**: `profile.toml` スキーマ、`candidates.jsonl` と承認コマンド、`review_by` による失効、履歴付き上書き、訂正の併記（AD-3）。

**採用しない機構**: 31 ディレクトリの記憶ツリー、LLM レビュアの自動適用、推論記憶の自動保存、ホット層の無出典エントリ、ナレッジグラフ、ベクトル索引（計測前）。

**測定方法**: 誤記憶事故（記憶が原因の誤出力）件数、候補の承認率、失効項目の割合、「知っているべきだった」イベント数、検索の Recall@5（ラベル付き 30 クエリ）。

## LP-5 強制はコードで、思考はモデルで（Enforce with code, reason with the model）

**原則**: 「毎回必ず起きるべきこと」（不可逆操作の確認、証拠の突合、私的領域の保護、ログ）は hook とスキーマで強制する。hook は ≤5、単一ディスパッチャ経由、各 <100ms、fail-open、LLM を呼ばない。それ以外の行動指針は ≤60 行の対話方針に留め、手順や思考の振付は書かない。方針の各行は「より賢いモデルならこの行は不要になるか」の問いを通過したものだけ残す（安全ゲート、検証済みの落とし穴、ツール契約、出力形式契約は残す）。

**必要な理由**: 散文ルールの実効遵守は 11–22%、hook でブロックすると 0% 違反（L-02, L-13）。公式 docs も「hooks are deterministic, CLAUDE.md is advisory」（T-I6）。同時指示数が増えるほど遵守率は落ち（T-G6/G7）、認知の振付はモデルを頭打ちにして腐る（L-28, T-D3）。

**防ごうとする失敗**: 散文ルールの腐敗、指示の過負荷、hook の堆積（LifeOS: 事故ごとに手順が積み上がり 56 hook）、hook のクラッシュによる停止、環境更新での hook 破損。

**採用する機構**: 6 hook（session-start / user-input / pre-tool / post-tool / stop / session-end、AD-7）、拒否リスト、スキーマ検証、対話方針 ≤60 行。

**採用しない機構**: プロンプトごとの分類器 hook、書式バナー強制、ナッジ、ドリフト警告、hook 内の LLM 推論、229 のワークフロー散文。

**測定方法**: hook 数と方針行数（テストで上限を強制）、硬いルールの遵守率（不可逆操作の無確認実行 = 0）、hook の平均実行時間、環境更新後の hook 破損件数。

## LP-6 人格は方針であって権限ではない（Persona is a policy, not an authority）

**原則**: Digital Assistant は「一貫した対話方針＋小さな表現設定」である。名前、一人称、ユーザー呼称、丁寧さ、温かさ、説明量、提案積極性、関係性を設定できるが、発言は証拠ではなく、記憶を直接書けず、計画はスキーマ検証されたカードであり、実行権限は環境の許可系と pre-tool ガードが持つ。自由記述は200文字、キャラクターブロックは220 tokensを上限とする。

**必要な理由**: ペルソナは精度を上げず（T-F1）、偏りを入れ（T-F3）、8〜100 ラウンドでドリフトする（T-F4, T-F5）。擬人化は非専門家の過信を強める（H-A5）。LifeOS の DA 実体（成長エンジン等）は非公開で、名前不一致による誤読み上げ事故があった（L-14, L-34）。一方、依頼が求める工学的価値（一貫性、方針保持、窓口統一、認識差検出、説明責任、連続性）は方針＋カード＋ログで満たせる。

**防ごうとする失敗**: 誤った権威付け、人格と判断権限の混同、擬人化による過信、長いペルソナによる文脈汚染、プロジェクト間のキャラクタードリフト。

**採用する機構**: `core/policy/interaction.md`（非権威条項を含む）、schema 2 persona、project scope、権限分離（AD-1）。

**採用しない機構**: backstory全文の常駐、音声、日記・意見の自動更新、ハートビート、人格による専門性・権限・承認省略。

**測定方法**: 未検証の提案を利用者がそのまま受け入れた割合、方針違反、現在指示の不遵守、事実性、出力量、実験 E3（personaあり vs なし）。

## LP-7 単一エージェント、一時ワーカー（Single agent, ephemeral workers）

**原則**: 主エージェントは一つ。ワーカーは (a) 独立した読取専用の並列調査、(b) 高影響タスクの独立検証、(c) 文脈が窓の 60% を超えるとき、に限り最大 3 つを一時的に起動する。ワーカーの指示書はタスクカードから生成し、ツール許可リストを付け、名前や人格は与えない。ワーカーは state に書込めず、≤1.5K tokens の構造化要約を返す。エージェント間の直接通信はしない。

**必要な理由**: 多エージェントの失敗率は 41–87%（T-E4）、効果は +80.8%〜−70.0% で課題構造に依存（T-E5）、トークンは ~15 倍（T-E7）、討論は計算量を揃えると勝たない（T-E13）。公式ガイダンスは「まず単一エージェントを最大化」（T-E10）。LifeOS は「並列化できるなら常に複数」を「腐った」として廃止した（L-18）。

**防ごうとする失敗**: エージェント間の文脈喪失、入力の無視、早期終了、検証欠如（MAST の失敗モード）、トークン爆発、人格による専門性の錯覚。

**採用する機構**: 環境ネイティブのサブエージェント（O-CC3, O-CX2, O-CU1）に生成した指示書を渡す（AD-8）。builder≠verifier の分離は新規文脈で担保。

**採用しない機構**: 階層型マルチエージェント、人名付き agent ロースター、他社モデルの常設、スウォーム、エージェント間メッセージ。

**測定方法**: ワーカー利用タスクの成功率と単一実行との差、トークン比（目標 ≤3 倍）、ワーカー返却の要約が主エージェントに引用された割合（実験 E4）。

## LP-8 リスク段階に応じた検証と人の確認（Risk-tiered verification and confirmation）

**原則**: タスクカードはリスク段階を持つ。R0（読取のみ）は検証なし。R1（可逆なローカル変更）はツール証拠。R2（外部に見える変更、共有リポジトリ、送信）は証拠＋独立検証（任意）＋実行前の要点提示。R3（不可逆: 削除、デプロイ、支払い、公開、`.env`）は実行前に利用者の明示確認、実行後に証拠。段階は下げられず、上げるのは自由。

**必要な理由**: 良性タスクでも 20–35% 失敗し、注入で 11–48% 乗っ取られる（T-I3）。状態を見ずに行動する誤り（T-I1）。利用者は完全委任を望まず machine-in-the-loop を強く選好する（H-F6）。自動化レベルは機能ごとに分けるべき（H-F4）。行動／対話／無行動の期待効用ゲート（H-F1）。

**防ごうとする失敗**: 誤った自律実行、不可逆操作の事故、一律に重い検証による遅延と演技、報酬ハック（T-H8）。

**採用する機構**: カードの `risk` 欄、pre-tool ガード（AD-7）、検証方針表（AD-9）、拒否リスト。

**採用しない機構**: 全タスク一律の第二の目、ブロックしないスペンド監査のような装飾的ゲート、`bypassPermissions` の常用。

**測定方法**: 無確認の不可逆操作件数（= 0 が要件）、R3 の確認で利用者が中止した割合（ガードの価値）、誤ブロック率、独立検証が捕捉した実欠陥数（実験 E5）。

## LP-9 利用者の判断を奪わない（Preserve the user's judgment）

**原則**: 意思決定型のタスク（何をするか、何を選ぶか）では、単一の推奨ではなく、≥2 の選択肢、トレードオフ、根拠、「これが間違う条件」を提示する。期限のある計画にはプレモーテムと、自分の履歴からの基準率を添える。目標と価値観は日付付きの仮説として保存し、催促や採点はしない。学びたい技能に関わる作業では、答えの代わりに手がかりを出す選択肢を用意する。創作・生成型のタスクではこの制約は緩める。

**必要な理由**: 人＋AI は決定課題で最良単独より劣り（H-B1 g=−0.27）、創作課題では上回る（+0.19）。説明は正誤に関わらず受容を増やす（H-A6）が、検証を安くする説明と認知強制は過依存を減らす（H-A7, H-A8）。「逆を考える」「反対理由を挙げる」は再現された脱バイアス法（H-D5, H-D6）。目標の過処方（H-E2）、計測の享楽低下（H-E5）、焦点化錯覚（H-E9）、答えを与える AI の学習阻害（H-C5）。

**防ごうとする失敗**: 自動化バイアス、認知的オフロードによる判断力の低下、目標の固定による探索の喪失、動機の侵食、誤った推奨の受容。

**採用する機構**: 意思決定支援テンプレート（AD-10）、プロファイルの目標に `review_by`、能動的な催促の不在、`hint` モード。

**採用しない機構**: 人生目標への山登り、euphoric surprise 採点、ハートビートによる提案、ダッシュボードのリング、単一推奨の既定化。

**測定方法**: 意思決定タスクで ≥2 案が提示された割合、利用者が推奨と異なる選択をした割合（0 でも 100% でもないのが健全）、決定後の差し戻し率、任意提案の採択率。

## LP-10 単一ログで観測し、自己改善は提案まで（One event log; proposals, not self-modification）

**原則**: 観測可能なものはすべて `events.jsonl` に追記する（セッション、カード、質問、仮定、ツール要約、証拠、訂正、候補、文脈マニフェスト、ワーカー）。`ctx report` がこれを集計する。系は自分の方針・hook・設定を書き換えない。書き換えるべき根拠があれば、証拠件数と廃止条件を付した提案を出し、人が適用し、適用後に evals を回す。

**必要な理由**: 外部信号なしの自己改善は頭打ちか自己欺瞞（T-D5, T-H2, T-H4）。自己改変エージェントは偽ログを作った（T-H6）。LifeOS 自身が hook・システムプロンプト・TELOS を手動限定にし（L-11）、Upgrades は「決して自動適用しない」（L-30）。観測がなければ「書き手のない読み手」は見えない（L-38）。自己申告は現実からずれる（H-B6）。

**防ごうとする失敗**: 観測不能な暗黙処理、自己改変による意図からの逸脱、Goodhart、ダッシュボード運用の負債、自己申告による誤った改善感。

**採用する機構**: `events.jsonl`、`ctx report`、`candidates.jsonl`（設定提案も同じキュー）、evals 20–30 件、`docs/DECISIONS.md`（AD-11, AD-12）。

**採用しない機構**: 自動のルール書換、反省コーパスの注入、夜間合成 cron、デーモンとダッシュボード、自己採点。

**測定方法**: 提案の受理率と適用後の回帰数、evals の失敗検出数、ログの欠落（イベント種別ごとの書込者の存在をテスト）。

## LP-11 共通コア、薄いアダプター（Common core, thin adapters）

**原則**: 中核は単一の CLI（`ctx`）と状態ディレクトリであり、環境に依存しない。アダプターは 4〜5 のイベント（session-start / pre-tool / post-tool / stop / session-end）とファイル規約（CLAUDE.md / AGENTS.md / .mdc）を翻訳するだけで、各環境 ≤3 ファイル。特定製品にしかない機能（システムプロンプト旗、メモリ機能、フォーク型サブエージェント）は必須前提にしない。

**必要な理由**: 初期対応するClaude CodeとCodexはどちらもhookを持つが、イベント名と入出力形式は異なる（O-CC2, O-CX2, O-AG1）。Claude Codeの更新でLifeOSのhookが壊れた履歴もある（L-37）。Cursorの調査結果は背景資料に残すが、v0.1 betaの対応対象にはしない。

**防ごうとする失敗**: 環境ごとの再実装、環境更新での破損、可搬性の喪失、hook の二重管理。

**採用する機構**: `ctx hook <event>` の単一入口、アダプターごとの薄いテンプレート（AD-13）。

**採用しない機構**: 環境固有デーモン、ランチャ経由でしか動かない憲法（LifeOS の `lifeos` alias 必須）、環境ごとの記憶機構への依存。

**測定方法**: wrapperの行数、host更新後の破損件数、同一evalsのClaude Code/Codex間の成功率差。

## LP-12 すべての構成要素は削除可能で、記録された失敗に対応する（Removable by construction）

**原則**: 機構・ファイル・hook・方針行を追加できるのは、イベントログに記録された失敗クラスが ≥3 回再発し、その機構が構造的に検査可能なときだけ。追加時に廃止条件を `docs/DECISIONS.md` に書く。ファイル数は目標 ≤60、上限 150（テストで検査）。四半期ごとに「書き手のない読み手」「30 日発火しない hook」「検索で一度も引用されない記憶」「複製された一覧」を探して削除する。

**必要な理由**: LifeOS は「事故ごとに手順が堆積」して 56 hook と 1,949 ファイルに達し、7 月に三分の二を削った（L-06, L-33）。公式ガイダンスも「必要になるまで複雑性を足すな」（T-E6, T-E8）。「一つのループに奉仕する」という採用基準は膨張を止められなかった（P14）。

**防ごうとする失敗**: 累積による腐敗、将来使うかもしれない構造、原則ごと・エージェントごとのファイル増殖、同じ情報の重複保存。

**採用する機構**: `docs/DECISIONS.md` の廃止条件、ファイル数テスト、四半期監査スクリプト（`ctx report --audit`）。

**採用しない機構**: 原則ごとのファイル、概念ごとのディレクトリ、空の将来用構造、装飾機能。

**測定方法**: 非 SKILLS ファイル数、hook 数、方針行数、監査で削除された項目数、廃止条件のない構成要素数（= 0）。
