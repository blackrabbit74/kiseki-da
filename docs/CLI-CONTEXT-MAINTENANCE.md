# CLIの権限と案件文脈の維持

通常のCLI操作も、タスク・検索履歴・取得記録を保存します。保存先がホストの書込範囲外なら、読取に見える検索でも権限エラーになります。OSのファイルモードと、実行ホストのsandboxによる許可は別に確認します。

## 同じ保存先で操作を再開する

1. 失敗したコマンドと同じ実行環境で `kiseki-da access --sid <現在のsession-id>` を実行します。案件内では `python3 .kiseki/entry.py access --sid <現在のsession-id>` を使います。Windowsは `py -3` を使えます。
2. `unavailable` のエラーが権限拒否なら、表示された保存先への今回のCLI操作をホストの権限確認に戻します。Codexで実行ツールが提供する昇格を使う場合は、そのツールの承認手順を通します。
3. 許可された実行環境で同じ診断を行い、元のコマンドを同じ引数・保存先・sessionで再実行して結果を確認します。すでに一部が成功している操作は、保存済みの状態を確認してから再開します。

`access` は専用の一時ファイルを作成・書込・削除する診断です。既存ファイルごとの書込可否は、元の操作で確認します。成功はそのプロセスの権限を示し、別のプロセスや次のセッションへの恒久許可を意味しません。起動中のホストが設定した書込範囲をCLI自身で変更する機能はありません。

新規案件は案件内の `.kiseki/state` を使い、起動時にも `.kiseki/entry.py` をCLI入口として案内します。これにより検索・タスク操作と案件生成・パック操作を同じ入口から利用できます。

## 文脈を更新する手順

新規案件の起動出力に、次の手順を含めます。手順自体も既存の推定2,500トークン・9,000文字の上限に算入します。

1. 常駐に、目的・必須制約・現在の決定・次の一手・詳細の取得先を選びます。
2. 次の判断に足りない情報を `task show` / `search` で取得します。必須制約の省略表示は `context required` の全ページで補います。
3. 進展したら現在の要点を更新・置換します。資料・理由・履歴・証拠は、出典と日付付きで案件の記録へ保存します。長期記憶は既存の承認手順に従います。
4. 案件生成や指示の更新後に `python3 .kiseki/entry.py context-audit --sid <現在のsession-id>` を実行します。超過時は重複を統合し、詳細を必要時に開く資料へ移して、取得先を残して再確認します。

`context-audit` はその時点のKiseki起動出力と、案件直下の `AGENTS.md` / `AGENTS.override.md` / `CLAUDE.md` / `.claude/CLAUDE.md` を候補として合算します。上限超過は終了コード2と `over_budget`、範囲内は終了コード0と `within_budget` を返します。文書を自動編集する操作はありません。

トークン数は既存の文字数ベースの推定です。ホスト共通指示、公開スキル、上位・下位フォルダの指示、会話履歴は測定外として表示します。候補が実際に読まれるか、測定外の文脈がどれだけあるかはホストで別途確認します。この検査は実対話でのモデルの追従率を証明するものではありません。

## 既存案件の案内を更新する

更新版の配布原本から、まず具体的な変更予定を確認します。

```sh
python3 /path/to/kiseki-da/install.py project refresh-guidance /path/to/project --sid <現在のsession-id>
```

表示された内容を適用する操作は次のとおりです。

```sh
python3 /path/to/kiseki-da/install.py project refresh-guidance /path/to/project --apply --sid <現在のsession-id>
```

対象は、既知の未変更beta.8で生成した入口です。現在の入口と固定runtimeのhashを照合し、手修正や未知の版を検出した場合は個別の差分確認に回します。

更新するファイルは `.kiseki/entry.py`、子孫への生成用テンプレート、`.kiseki/project.json` の3つです。manifestには更新前後を追えるhashとtransactionを記録します。既存runtimeは同じ版を保ち、この明示的な案内更新によるhash変更を記録します。元のファイルは `.kiseki/transactions/<id>/` にバックアップし、途中失敗時はtransactionが復元します。

更新後は新しいセッションを開始し、ホストが求める信頼確認を行ってから `access` と `context-audit` を確認します。既存の独自指示で超過が出た場合は上の手順で要点と参照先を整理します。既存の稼働セッションへの反映、アプリでの信頼確認後の連続対話は別途検証が必要です。
